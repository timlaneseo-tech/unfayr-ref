# Ref v1 benchmark: Ref vs Claude alone

Date: 2026-10-05 · Skill: `ref/` on branch `feat/ref-v1` · Evals: `evals/evals.json` (7 scenarios, 61 assertions: 36 behaviour, 25 `[file]`)

## Headline

**In 7 test scenarios (one run each, graded by Claude), Ref passed 32/36 behaviour checks vs 25/36 for Claude alone.** That is 88.9% vs 69.4%, from the first run, before any fixes. The evals were written alongside Ref and encode its rules (see Caveats), so this measures how well each arm follows Ref's way of running a review, not general helpfulness. Counting all assertions, including the review-file checks, it was 56/61 (91.8%) vs 31/61 (50.8%).

After two small skill-content fixes, I reran the two scenarios Ref had failed. In that rerun Ref passed all 11 behaviour checks and Claude alone passed 7 of 11. If those reruns replace the first-run results for those two scenarios, the totals become 36/36 behaviour and 60/61 overall for Ref, and stay at 25/36 and 31/61 for Claude alone. That composite is not a fresh run of all seven scenarios, and the iteration-2 fixes originally used examples drawn from the scenarios, so neither the iteration-2 nor the composite numbers are held out. Keep them out of any published line; quote only the iteration-1 sentence above, with its qualifier.

`[file]` checks grade the structured review file. Claude alone has no such file format, so it fails most of them by construction. The behaviour-only row removes that format advantage, since any answer can pass those checks in plain words, but the behaviour checks still encode Ref's rules (see Caveats).

## Method

- **Command, both arms:** `claude -p "<eval prompt, verbatim>" --model sonnet --output-format text --setting-sources project,local --strict-mcp-config --dangerously-skip-permissions`. The run used Claude Code 2.1.289. The `sonnet` alias resolved to `claude-sonnet-5-5` in every session log. Each run had a 600 s timeout. The longest took 57 s, so there were no timeouts.
- **Isolation:** each run had its own fresh directory, `%TEMP%\ref-bench\<iter>\<id>--<arm>\`. It held only that scenario's fixture files, at the same relative paths the prompt uses (`evals/files/...`).
  - **Ref arm:** `ref/` was also copied to `<dir>\.claude\skills\ref\` as a project skill. The prompt does not name the skill. Ref had to trigger from its description.
  - **Baseline arm:** no skill.
  - Nothing was installed in `~/.claude/skills`, and no user settings were changed. `--dangerously-skip-permissions` was used only inside these throwaway directories.
- **Isolation probe:** I ran one cheap run with the same flags in a temp directory with the skill installed, and asked it to list its skills, MCP servers and injected context. It reported:
  - Skills: `ref` plus Claude Code's built-ins only (dataviz, update-config, keybindings-help, code-review, simplify, fewer-permission-prompts, loop, schedule, claude-api, run, plugin-authoring, init, security-review).
  - MCP: none.
  - CLAUDE.md, hooks and session-start context: none. The only injected context was the account email and the git attribution reminder.
  - None of the user's personal skills or plugins loaded (the usual list is about 200). Both arms ran under identical conditions; the baseline differed only by the missing `ref` folder.
- **Prompts:** taken verbatim from `evals.json`, with no hints. Each scenario is a single turn. If a run stopped to ask a question, that question was its answer.
- **Captured per run:** `runs/<iter>/<id>-<name>-<arm>/` holds four things:
  - `transcript.txt`: stdout, the final answer.
  - `meta.txt`: exit code and seconds.
  - `tool-trace.txt`: every tool call, extracted from the headless session log. This shows whether the `ref` skill was actually invoked.
  - `outputs/`: every file the run created or modified.
- **Grading:** every assertion was graded PASS or FAIL with a one-line evidence note, in `2026-10-ref-v1.grades.json`. `[file]` assertions were checked against the review file the run produced. `review_file.py validate` was run on every produced file. Baseline runs were graded against whatever tracking file they wrote, if any. `harness/tally.py` computes every number in this document from the grades file.
- **Harness:** `harness/run_one.sh` is the per-run script. `harness/trace.py` does the tool-trace extraction. One cosmetic bug: the scenario-name lookup in `run_one.sh` failed under Git Bash, so the temp directories are named `<id>--<arm>`. The fixtures and prompts were copied correctly, which I verified per run, and the saved run folders carry the full names.
- **Iteration:** after iteration 1, I fixed two skill-content defects, in `ref/SKILL.md` and `ref/references/intake.md`. `python -m unittest discover -s tests` stayed green. I then reran only the failed scenarios (S6, S7), both arms. In total there were 18 benchmark runs plus 1 probe, within the 28-run budget.

## Caveats

- **Small sample:** 7 scenarios, one run per arm per iteration. There was no repeat sampling, so these numbers do not show variance. One assertion flipping moves behaviour scores by about 3 points. The baseline reruns of S6 and S7 scored the same as in iteration 1 (5/10 and 3/6). That is weak evidence of stability, not a measurement.
- **Model:** `claude-sonnet-5-5` via Claude Code headless mode, for both arms. The results may not carry over to other models, to claude.ai, or to the desktop app.
- **Same-agent grader:** the grader is the same agent that ran the benchmark and fixed the skill (Claude Opus 5.5). It is not blind and not independent. Every grade has a quoted evidence note, and the transcripts and files are saved, so anyone can re-grade.
- **Fixes informed by the eval:** both iteration-2 fixes were written after seeing the iteration-1 failures. Iteration 2 is therefore not a held-out test.
- **S1-S5 were not rerun after the fixes:** a regression from the iteration-2 description and intake wording, or from the later post-benchmark fix (commit 1817a7e), is unlikely but untested. This is why the composite row is labelled as a composite, and why the iteration-1 number is the one to quote.
- **`[file]` assertions favour Ref by design:** they check Ref's own file format and validator. The behaviour-only numbers remove that format advantage but not the rule bias above. Claude alone could only pass them by coincidence: S3 and S5, where it edited an existing Ref file, and S7, where no file is required.
- **S3 is a Ref behaviour failure:** Ref labelled the reversal but did not create the conflict entry its own `conflicts.md` asks for, so the lock was not cited in the file and the decision did not show under "Decisions to make". The eval wording ("its text cites lock L1") is also slightly ambiguous, because a comment's quote must stay verbatim; the natural place for the citation is the conflict recommendation. I fixed the skill text after the benchmark (triage.md and conflicts.md). That fix is not re-measured, and the published numbers include the FAIL.
- **Iteration-2 examples were drawn from the scenarios:** the iteration-2 fix used an example in the SKILL.md description ("Legal won't allow it, rewrite the headline") close to the S7 prompt, and an example in intake.md ("Dana mentioned on the call...") close to the S6 fixture. Both have since been replaced with unrelated wording (commit 1817a7e), but the iteration-2 runs used the originals. So the iteration-2 and composite numbers are not held out and should not be published.
- **The evals encode Ref's rules:** the scenarios and assertions were written alongside Ref, and several reward Ref's specific policy rather than a generally better answer. For example, S7 rewards refusing to write headlines (Claude alone did what the user asked), S6 #5 rewards asking whether to add a relayer as a reviewer, and S5 #5 rewards offering a choice of next steps. The gap measures how well each arm follows Ref's review method; it is not a neutral quality comparison.
- **Borderline grade:** in S7 iteration 2, Ref's decline is three short sentences, against the "one or two sentences" assertion. I graded it PASS. If it is graded FAIL, iteration-2 Ref behaviour becomes 10/11 and the composite becomes 35/36.
- **Single-turn constraint:** scenarios that would normally involve setup questions ran as a single turn. Both arms answered with clarifying questions where needed, and those were graded as the answer.
- **Fixture dates:** the fixture dates (Oct 6-14) are later than the run date (Oct 5). Several runs in both arms flagged this as a possible data issue. It did not affect any grade.
